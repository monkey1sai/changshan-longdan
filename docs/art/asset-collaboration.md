# 模型資產協作契約

契約版本：1。適用於本遊戲 repo 的模型資產工作；本文件由 Git 管理。
此契約補充既有專案規範，不豁免權限、審查、測試與發布要求。

## 1. 預設需求路由與責任

新增、替換或修改模型、材質、骨架、動畫、碰撞代理、LOD 時，先確認可重用資產及授權；仍需製作或修改時，預設向 `mmo-asset-pipeline` 美術工程師提出需求。
遊戲端負責需求、整合、遊戲內驗收與修改回饋；美術端負責製作、匯出、交付清單與製作端檢查。
交付方自評不能代替遊戲驗收，也不得虛構人工簽核。
工程師可為人員或已授權 agent；沒有送達、接單或執行機制時，不得聲稱已委派或背景製作中。跨 chat 訊息仍須符合當次授權。

流程受阻可在已授權範圍使用明確標示的占位資產推進工程，不得算正式交付。
正式改用其他來源須記錄原因與授權依據；需要新增權限時只請求具體缺少的授權。
美術工作區未開啟不是跳過委託流程的理由。

## 2. 工作區與安全 clone

1. 先查已登記或使用者指定的工作區，核對 repo 身分、來源、分支與 Git 狀態，不只依資料夾名稱。
2. 找不到時，使用受信任設定或使用者確認的 repo URL，在授權父目錄下建立獨立 clone；不得猜測同名遠端。
3. clone 前記錄 Authorization Envelope：目的地、目的、允許操作、傳輸資料、禁止操作、停止條件。保守預設僅取得指定 repo，不執行內容或上傳本機資料。
4. 目標已存在不得覆寫、清空、reset、clean、搬移或 stash。確認可用則依規範重用，否則選新的不衝突路徑並記錄。
5. 修改前讀取適用 AGENTS.md／CLAUDE.md、相關來源並檢查 Git；髒工作區、治理或並行工作使用隔離工作樹，保留既有編輯。
6. 不自動執行 hooks、安裝、子模組初始化、生成或服務啟動；先檢查內容與權限。hooks 維持停用。
7. 使用既有受支援的認證，不讀取或輸出憑證。來源不明、認證失敗、主機金鑰異常或權限不足即停止該步，記錄恢復條件，不繞過保護。

## 3. 需求契約

每項需求使用固定 `request_id`，存於 `docs/art/requests/<request_id>.md`，至少記錄：

- 目的、使用場景、優先順序、整合與驗收負責人。
- 風格、輪廓、比例、顏色、參考來源、使用權、資料分級與可接受差異。
- 引擎與版本、格式、單位、朝向、原點、尺寸、材質、骨架／動畫介面、碰撞與 LOD；不適用項目明寫。
- 三角面數、材質數、貼圖尺寸、骨骼數及相關預算；效能指定裝置、場景負載、量測方式與門檻。
- 驗收場景、鏡頭、需操作動作、必須保留的玩法契約、證據與失敗標準。
- 原始檔與執行用檔案、授權限制、外部服務、私有資料傳輸及付費額度的允許範圍。

未知標記 `TBD`。會影響製作或驗收的必要條件未定時，只推進獨立工作，不得自行視為已確認。

## 4. 通用性與遊戲端邊界

美術核心流程、模板與工具不得硬編碼本遊戲、角色、風格、專用路徑或玩法。
風格、尺寸、預算、引擎輸出以需求參數、可選設定或獨立匯出介面表達。
遊戲 repo 管理匯入設定、場景包裝、碰撞層、動畫狀態機、程式綁定與玩法數值。
通用工具修正與單一資產製作應可分別審查；不得把遊戲特例變成全域預設。
私有參考與資產只存於權限相符的位置，不放入公開範例或共用測試資料。

## 5. 交付契約

每次交付固定 `asset_id` 並使用新的 `delivery_id`；manifest 存於 `docs/art/deliveries/<delivery_id>.json`，至少包含：

- 需求 ID 與需求版本／commit、資產及交付版本。
- 製作來源 repo commit；工作樹非乾淨時附差異與受控快照，不宣稱能由 commit 單獨重現。
- 製作工具版本、匯出設定、已知限制及適用的生成工作識別，不含憑證。
- 每個檔案的相對路徑、用途、大小、SHA-256。
- 原始可編輯檔、模型、貼圖、骨架、動畫、碰撞與 LOD 的有無、狀態及實測統計。
- 製作端檢查結果、作者／來源、授權及再散布限制。

檔案須能取得且雜湊相符；只有預覽、截圖或未保存的雲端工作不算交付完成。
明確區分靜態模型、已綁骨架、可播放指定動畫、已整合與遊戲內驗收通過。
既有 manifest 可保留並以 ID 關聯交付紀錄；不默默改寫既有格式或消費程式。

## 6. 遊戲內驗收

整合前核對需求、manifest、雜湊與授權；不符即回報，不默默修補後宣稱原交付合格。
保留前一可用版本，於隔離分支／工作樹整合。先執行相關確定性檢查，再進行遊戲內操作：

- 核對尺寸、方向、材質、動畫、碰撞、鏡頭可讀性與指定場景。
- 驗證需求指定的移動、攻擊、受擊、死亡或互動；不得未經授權改變傷害、命中、移動或權威判定。
- 記錄被測遊戲 commit、delivery_id、引擎、裝置、場景、步驟、預期／實際結果及可取用的證據。
- 工程、視覺、遊戲操作、效能與授權分開報告；合成輸入標示清楚，不代稱真人操作。
- 匯入成功、單獨模型預覽、無頭測試不能代替遊戲內操作；本機通過不代表部署或發布。
- 涉及部署後真實站點驗收時，依專案規則使用使用者可觀看的 Chrome，逐步操作並提供截圖。

必要檢查失敗、缺失或環境受阻不能算 PASS。授權的驗收者依完整證據標記 ACCEPTED；沒有具體授權不得推定人工簽核。

## 7. 修改與回歸

沿用 request_id，逐項建立問題編號，附交付版本、重現步驟、預期／實際、證據與修正通過條件。
區分美術缺陷、整合缺陷與新增需求：整合缺陷由遊戲端修正，外觀、骨架或交付契約變更回美術端。
新增需求更新需求版本及範圍／預算／授權，不偽裝成原規格缺陷。
必要臨時修補保留差異並回饋，避免形成未記錄的第二份製作來源。
美術端產生新 delivery_id，列修正、未解決與相容性變更，不覆寫舊交付。
遊戲端驗證修正及受影響回歸；遵守既有重試預算，沒有新證據、假設或方法不得無限重試。

## 8. Git 與版本追溯

Git 管理本規範、需求、交付 manifest、驗收紀錄及資產鎖定清單：
- `docs/art/requests/<request_id>.md`
- `docs/art/deliveries/<delivery_id>.json`
- `docs/art/acceptance/<request_id>/<delivery_id>.md`
- `assets/art-assets.lock.json`

上述路徑在真實需求／交付發生時建立，不以空白紀錄偽造已交付或已驗收。
鎖定清單包含 asset_id、delivery_id、來源 commit、檔案雜湊與受控儲存位置，不能只指向 latest 或浮動分支。
大型檔案依 repo 政策使用 Git LFS 或受控儲存；確認實際物件可取得，不能只有指標。
整合 commit 與驗收紀錄互相追溯；事後提交文件須明確標示被測 commit 與後續文件差異。
保留合法可取得的前版檔案與鎖定資訊；回退亦須驗證相關行為。
已 ACCEPTED 的交付若內容或整合行為改變，必須重新驗收；不得沿用舊證據覆蓋新版本。
本契約不自行授權 commit、push、PR、merge、部署或其他遠端寫入，各依當次明確授權及 repo 規則。

## 9. 私有資料與外部服務

資料分級 public／internal／restricted；未分類按 restricted。
僅交付必要資料，不預設傳送完整遊戲 repo、未公開劇情、玩家資料、內部日誌或無關原始碼。
私有內容不得進入公開 repo／issue／下載點／範例；repo 存取權不等於第三方轉傳權。
外部生成、轉檔、儲存與付費額度須符合具體授權的服務、用途、資料範圍及費用，否則停在本機準備。
每次外部寫入前記錄 Authorization Envelope；紀錄本身不含秘密。
不得把 token、密碼、SSH key、.env、含憑證 URL、臨時簽名 URL 寫進 Git、manifest、聊天或證據。
審查截圖及交付中非必要的使用者路徑、帳號、主機名、隱藏內容與中介資料，同時保留合法來源及授權證明。
若目前遊戲 repo 的可見性不允許儲存某資料，Git 只存去敏識別與受控位置；原始需求、素材與證據留在授權儲存，不強迫提交私有資料。
.gitignore 不會移除歷史；發現洩漏須停止散布並回報，不擅自改寫歷史、刪遠端或更動憑證。

## 10. 狀態與完成界線

流程：DRAFT → READY → IN_PROGRESS → DELIVERED → INTEGRATING → ACCEPTED。
退修使用 CHANGES_REQUESTED，阻礙使用 BLOCKED 並記錄原階段、原因及恢復條件。
DELIVERED 只表示可檢查交付到位；ACCEPTED 須有該版本全部必要驗收證據。
本文件是作業契約，未實作的自動檢查或存取控制不得宣稱已生效。
